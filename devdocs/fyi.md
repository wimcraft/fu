# FYI

## 2026-09-13 — Automate macOS releases and reposition as a composable viewer

- **Product description:** removed the typing-practice framing. `fu` is a fast, keyboard-driven image viewer for macOS terminals, inspired by `sxiv` and intended to compose with Newsboat, `lf`, and shell scripts.
- **Release workflow:** a `v*` tag now builds and tests native `aarch64-apple-darwin` and `x86_64-apple-darwin` binaries on GitHub-hosted Apple Silicon and Intel runners. Archives are checksummed and attached to a generated GitHub Release. Manual dispatch can publish an existing tag, but the already-pushed `v0.1.0` is intentionally left without retroactive assets; automation begins with the next tag.
- **Installer:** `install.sh` detects Apple architecture, downloads the matching latest or requested release archive, verifies it against `SHA256SUMS`, and installs to `${FU_INSTALL_DIR:-$HOME/.local/bin}`. It fails closed for unsupported operating systems, architectures, missing checksums, and mismatches.
- **Evidence:** release workflow YAML and installer shell syntax parse successfully; the exact Apple Silicon workflow test command passes all 73 tests; the release target builds as a Mach-O arm64 binary. A hermetic installer smoke test downloaded mocked release assets, verified the checksum, installed a byte-identical executable, and separately rejected a deliberately invalid checksum without installing.

## 2026-09-13 — Make navigation placement-only; add whole-image fit

- **Performance problem:** every pan, page, and zoom created a new source crop, resized it to pane pixels, base64-encoded it, and transmitted a new Kitty image. Moving an already-decoded image therefore still waited on image processing and a pixel payload.
- **Decision:** PNG-compress and upload the full source once, keep one identified Kitty image and placement in the terminal, and update navigation with Kitty `a=p` source rectangles (`x`, `y`, `w`, `h`) plus a width or height constraint. The background worker only prepares the initial upload; terminal output remains on the UI thread. Reusing the same image and placement ids also bounds terminal image storage, and `TerminalGuard` deletes that identified image on every exit path.
- **Whole-image fit:** `View` now distinguishes width fit from whole-image fit. `f`, or zooming out once from zoom `1`, selects the complete source and limits its placement by whichever pane dimension preserves its aspect ratio. Zooming in returns to width fit; `0` still resets to width fit at the top-left.
- **Evidence:** the complete test suite passes with 53 unit tests, 12 CLI tests, 6 real-PTY tests, and 2 protocol integration tests. The real-PTY regressions observe that a scroll emits `a=p` without `a=t`, and that a 64×256 portrait source is placed as `x=0,y=0,w=64,h=256,r=22` in an 80×24 / 800×480 terminal. `cargo clippy --all-targets -- -D warnings` and `cargo build --release` also pass.
- **Manual gap:** the direct placement path has not yet been visually exercised in a real Ghostty tmux pane in this session; tmux wrapping is byte-tested against the same DCS form previously used by `ratatui-image`.

## 2026-08-05 — Fix focus-dependent corrupted rendering: redraw only on change

- **Bug found via manual Ghostty testing:** the image showed only a thin, empty-below sliver while the `fu` pane had focus, but rendered completely and correctly the moment focus moved to a different pane. Added a temporary debug status line (`crop=`/`draw=`/`src=` numbers) to rule out a geometry/aspect-ratio bug first — the numbers were sane (crop equalled the full source at zoom 1, as expected), and the focus-dependence itself ruled out a pure math bug anyway: a wrong aspect ratio would misrender regardless of focus.
- **Root cause:** `app.rs`'s event loop called `terminal.draw()` unconditionally on every loop tick (~every 16ms, whether or not `event::poll` returned anything), and `StatefulImage`'s render path re-sends the Kitty placement on every draw. That's roughly 60 redundant Kitty transmissions per second of an unchanged image. While the pane had terminal focus, Ghostty apparently has to composite that stream against a live blinking cursor, and this specific case corrupted the visible result; unfocused, there's no cursor to reconcile against and it settled on the correct final frame.
- **Fix:** added a `needs_redraw` flag, set only when something actually changes (a render completes, a resize response applies, a key is processed, a resize event fires) and cleared right after the one `terminal.draw()` call that follows. Idle loop ticks now skip drawing entirely. This is also just better practice for a Kitty-graphics TUI in general, independent of the specific Ghostty/focus interaction.
- **Removed:** the temporary `debug_status_line` diagnostic, once it had served its purpose of ruling out the geometry hypothesis.

## 2026-08-04 — Fix tmux blank-pane bug; add i/o zoom keys

- **Bug found via manual tmux testing:** with `allow-passthrough on` and everything else working (direct Ghostty was fine), the tmux pane rendered nothing — a black rectangle — while the status line still said `ready`, meaning `fu` believed the render succeeded. Root cause: `ratatui_image::picker::Picker`'s own, *separate* `is_tmux` flag (which controls whether Kitty output is wrapped in the DCS passthrough sequence tmux requires) is decided purely by a private heuristic — `$TERM` starting with `"tmux"`, or `$TERM_PROGRAM == "tmux"` — completely independent of `$TMUX`, which is what `terminal::check_tmux_passthrough` (and the spec) treats as authoritative. Many tmux configs report `TERM=screen-256color` or similar, which doesn't match that heuristic; the picker then silently decides it's *not* in tmux and sends unwrapped Kitty escapes, which tmux correctly drops since passthrough only recognizes the wrapped form. There's no public setter for the picker's `is_tmux` (it's `pub(crate)`), so the only lever from outside the crate is the env vars its heuristic reads. Fixed in `protocol::init_picker`: when our own `$TMUX`-based `is_tmux` is true and the picker's heuristic wouldn't already agree, set `TERM_PROGRAM=tmux` before constructing the picker (left `TERM` itself untouched, since other code — `crossterm` included — may rely on it for real capability negotiation, and `TERM_PROGRAM` is a much narrower, less load-bearing signal).
- **Added (user request, not in original SPEC):** `i`/`o` as additional zoom in/out keys, alongside the existing `+`/`=` and `-`/`_`. The symbol keys are uncomfortable on some ergonomic keyboards (reported on a Moonlander); `i`/`o` are unshifted and mnemonic ("in"/"out"). `SPEC.md` §6 and `README.md` updated.

## 2026-08-04 — Fix `Resize::Crop` misuse; add position bars

- **Bug found via manual Ghostty testing:** the image only ever showed a small, unscaled top-left slice of the intended viewport, worse at larger panes/zoom. Root cause: `render.rs` and `app.rs` used `ratatui_image::Resize::Crop`, whose `resize_pixels` implementation literally calls `image.crop_imm(x, y, width, height)` — it truncates raw pixels at native size, it does not scale. `fu` already does its own semantic viewport crop in `view.rs`; handing that to `Resize::Crop` again just chopped it down to whatever the target pixel size happened to be instead of scaling it to fill. Fixed by switching both call sites to `Resize::Scale`, which actually resizes to the target — matches the design intent (view.rs crop selects *which* source region; ratatui-image's resize step should only ever scale it, never crop again).
- **Added (user request, not in original SPEC):** two position bars showing where the current crop sits within the full source extent on each axis, since a plain `x=`/`y=` pixel count gives no felt sense of how much image is left in any direction. First cut put both bars as text rows above the status line; on follow-up feedback ("why not vertical on the right, like most apps"), moved to a conventional scrollbar layout instead — a vertical bar (one character per row) in a reserved right-hand column alongside the image, a horizontal bar in a reserved bottom row under the image, plain-text status below that, and the bottom-right corner cell left blank like a real scrollbar corner. Implemented as `terminal::vertical_bar`/`horizontal_bar`/`status_line`, laid out by `app.rs`'s draw closure. `view::Geometry` gained `draw_columns` (mirroring the existing `draw_rows`) and `STATUS_COLS = 1`; `STATUS_ROWS` settled at `2` (bar row + text row, since the y-bar moved off the bottom). `render.rs`'s resize target now uses `draw_columns` instead of the raw terminal column count. `SPEC.md` §3/§7.1 and the one `view.rs` test with a hardcoded expected crop height were updated for the new constants.

## 2026-08-04 — Restore reliable terminal navigation

- **Problem:** The cache rewrite pre-rendered `chafa` output in a background shell. Chafa probes the controlling terminal independently of redirected standard streams, so the worker could consume navigation keys and leave the foreground loop apparently frozen. It also competed with uncached horizontal rendering.
- **Decision:** Keep MPC source conversion and terminal-output caching, but limit background prefetch to ImageMagick crop-and-resize work. Chafa now runs only in the foreground. Queued navigation keys are coalesced before one redraw.
- **tmux behavior:** When tmux has `allow-passthrough` disabled, the default format changes to `symbols`; `fu` must not emit Kitty deletion sequences in that mode. An explicit `-f` choice remains authoritative.
- **Lifecycle:** Cache paths include the display shape, making a stale worker unable to publish a raster for a resized or re-zoomed pane. Cleanup cancels cooperatively and waits for the active raster worker rather than killing its shell and orphaning a child process.
- **Evidence:** PTY regressions cover tmux fallback, a prefetch worker that attempts to read `/dev/tty`, and a burst of panning keys. A live symbols-mode rapid-panning smoke test exited 0 after forty navigation inputs; a tmux-mode smoke test with passthrough off emitted zero Kitty escape sequences and rendered symbols.

## 2026-08-04 — Rust terminal viewer MVP specification

- **Decision:** Replace the Bash implementation cleanly with an in-process Rust `fu` binary. The MVP targets Ghostty pixel graphics through tmux, keyboard-only controls, and latest-input-wins rendering.
- **Why:** The Bash process model retains a first-render subprocess latency floor and cannot safely let a background Chafa process coexist with terminal input. Incremental tuning would preserve those constraints.
- **How:** `SPEC.md` uses `ratatui-image` rather than reimplementing Kitty transport. The library provides Ghostty-tested, tmux-aware Unicode-placeholder rendering, pixel probing, and threaded encoding; `fu` retains viewport state, input coalescing, tmux policy, and PTY acceptance tests.

## 2026-08-04 — Rust MVP implemented, clean cutover complete

- **Decision:** Implemented the full MVP per `SPEC.md` §15 (Tasks 1–5) and cut over: the Bash `fu` script, `tests/test_fu.py`, and all ImageMagick/Chafa references are deleted in the same change. Installed binary stays named `fu`, built via `cargo install --path .`.
- **Pixel-size querying is fully owned by `ratatui-image`.** §7.1 reads as if `fu` should re-implement `TIOCGWINSZ` plus `CSI 16 t`/`CSI 14 t` fallback itself, but §8.2 explicitly forbids duplicating the library's terminal pixel query code — and `Picker::from_query_stdio()` already performs exactly that query (including its own temporary termios toggle) as part of capability detection. Resolution: `terminal::geometry()` takes the `FontSize` the picker already measured and combines it with `crossterm::terminal::size()` (itself a `TIOCGWINSZ` read) for columns/rows. No CSI query code lives in `fu`.
- **`ThreadProtocol` is used, but not as the primary path.** §7.3.5 says to use `ratatui_image::thread::ThreadProtocol` for resize/encode with its completion id as "the render generation." In practice, a viewport pan/zoom needs an entirely new *source crop* (new image bytes), which `ThreadProtocol`'s own request/response channel can't produce — it only re-resizes image data it already holds. `render.rs`'s own worker does crop → `new_resize_protocol` → `resize_encode` fully, off-thread, tagged with `fu`'s own `generation: u64` (matches the `RenderRequest`/`RenderResult` interfaces in §9 exactly). `ThreadProtocol` still holds the widget state and still services its own `ResizeRequest`/`ResizeResponse` channel — polled by the *same* worker thread alongside `fu`'s own channel, so "one rendering worker" stays literally true — as a correctness safety net for the rare case where geometry changes between a crop being queued and applied.
- **tmux gate ordering matters for correctness, not just UX.** `Picker::from_query_stdio()`'s tmux detection path calls `tmux set -p allow-passthrough on` itself as a side effect (visible in the library source) — which would violate "the MVP does not auto-edit tmux configuration" if ever reached with passthrough off. `main.rs` therefore always runs `terminal::check_tmux_passthrough()` (our own `tmux show-option -gqv allow-passthrough` check) *before* constructing a `Picker` at all, so a disabled passthrough is rejected without the library ever touching tmux config.
- **Signal handling and the pty test harness both use raw `extern "C"` FFI instead of a new dependency**, since §10 only allows `ratatui`, `ratatui-image`, `image`, `crossterm`, `clap`, `thiserror`. SIGINT/SIGTERM are caught via a directly-declared `signal(2)` (needed because raw mode's ISIG suppression only covers tty-generated signals, not ones delivered via `kill`). `tests/pty.rs` drives the real binary over a real `openpty()`-allocated pty and answers its Kitty-capability probe with a synthetic response, so the whole raw-mode lifecycle is exercised without a real terminal.
  - Two Apple-arm64-specific pitfalls hit along the way, both root-caused by actually running the code rather than guessing: (1) `ioctl` must be declared as C-variadic (`fn ioctl(fd: i32, request: u64, ...) -> i32`) — declaring its trailing pointer as a fixed parameter instead passes it in a register while Apple's ABI expects variadic args on the stack, so the real syscall reads garbage and fails `EFAULT`. (2) Once a session leader with a pty as its controlling terminal exits, BSD hangs up the *slave* side for every process holding it, not just the exiting one — so a test harness that reuses one `slave_fd` across two sequential `login_tty()`-based spawns gets `EBADF` on the second spawn even though the fd is nominally still open. Fixed by reading terminal state (`TIOCGETA`) via the unaffected *master* fd instead of spawning a second diagnostic process.
- **Evidence:** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` (40 unit + 12 CLI + 3 protocol + 4 real-pty integration tests), and `cargo build --release` all pass. The pty suite genuinely enters raw mode, survives a 40-key `hjkl` burst, and confirms canonical/echo mode is restored after `q`, SIGINT, and SIGTERM — verified by reading `c_lflag` before/during/after via the pty master, not by inspecting exit codes alone.
- **Not verified in this session:** the manual Ghostty/tmux acceptance run in §12 (real Kitty rendering, real pane resize, real `allow-passthrough` toggle) — no interactive terminal was available. Needs a manual pass against a real 30 MB screenshot before this is fully sign-off ready per §12/§14.
